# Processing a GeoPackage into calculator test data

This note describes how raw `.gpkg` files (typically kaava / zoning exports
in EPSG:3067) are turned into the zipped GeoJSON blob that the
`POST /calculation` endpoint consumes — i.e. the same shape as
[tests/data/test-data-small-polygon.zip](../tests/data/test-data-small-polygon.zip).

The main test flow lives in [tests/api/main_test.py](../tests/api/main_test.py).
It uploads the zip via `POST /calculation`, drives the worker with
`calculate_piece`, and then compares the returned per-area /
totals properties against a reference
[tests/data/test-data-small-polygon-results.geojson](../tests/data/test-data-small-polygon-results.geojson).
Any new gpkg fixture can slot into this flow as long as:

1. It is a zip containing a single file literally named `file`.
2. That file is a GeoJSON `FeatureCollection` in EPSG:4326.
3. Each feature carries the plan-level properties the API expects
   (`id`, `area_ha`, `name`, `zoning_code`, `geometry_mode`, `selected`),
   plus optional `landuse_*` percentages.

## Why an override for zoning / landuse

Real `.gpkg` sources almost never carry a `zoning_code` column that matches
what the calculator uses, and they almost never have the four
`landuse_built / landuse_new_open_vegetation / landuse_new_tree_vegetation /
landuse_existing` percentages. Without them the calculator either errors out
or silently falls back to `existing = 100 %`, neither of which is useful for
testing specific scenarios.

The conversion script therefore exposes a **dev override**: you pass a single
`zoning_code` and (optionally) a single landuse distribution on the command
line, and the script stamps those values onto **every** feature. If the plan
has multiple zoning areas, they are all overridden with the same dev-specified
class and distribution. This makes calculation results deterministic and lets
tests target a specific code path (e.g. `AK` with a heavy `new_tree_vegetation`
share to exercise the forestry curves).

## The script

[tests/data/gpkg_to_testdata.py](../tests/data/gpkg_to_testdata.py).

It:

1. Opens the first layer of the `.gpkg` with `geopandas.read_file` (or a
   specific layer via `--layer`).
2. Reprojects to EPSG:4326. The upload pipeline in
   [app/main.py:144](../app/main.py#L144) reads the zip and then calls
   `set_crs("EPSG:4326", allow_override=True)` **without reprojecting**,
   so the file must already be in lon/lat.
3. Filters out non-polygon / missing geometries and repairs invalid ones with
   `buffer(0)`, mirroring the ingestion pipeline so we fail early here rather
   than in the worker.
4. Computes `area_ha` in EPSG:3067 (TM35FIN) since the source data is Finnish.
5. Replaces all per-feature properties with the minimal plan-shape dict, using
   the override values for `zoning_code` and (if provided) the four
   `landuse_*` percentages.
6. Writes the GeoJSON into a zip entry literally named `file`, matching
   the shape expected by `process_and_create_plan` in
   [app/main.py:144](../app/main.py#L144).

## Running it on `test_data_2026_04_15.gpkg`

The `test_data_2026_04_15.gpkg` fixture contains a single Helsinki-area
kaava MultiPolygon (layer `pappila`, ~3.2 ha) with no usable plan columns —
so the override is mandatory. The command used to produce
[tests/data/test_data_2026_04_15.zip](../tests/data/test_data_2026_04_15.zip)
was:

```bash
python tests/data/gpkg_to_testdata.py \
    tests/data/test_data_2026_04_15.gpkg \
    tests/data/test_data_2026_04_15.zip \
    --zoning-code AK \
    --landuse 20,40,30,10
```

This produces one feature with:

- `zoning_code = "AK"` (residential — picks the calculator's standard urban
  curve; swap for another code to exercise a different branch).
- Landuse split: 20 % built / 40 % new open vegetation / 30 % new tree
  vegetation / 10 % existing cover.
- `area_ha ≈ 3.22`.

## Plugging a new fixture into the test suite

The existing API test hardcodes
`TEST_DATA_PATH = Path("tests/data/test-data-small-polygon.zip")` and an
`EXPECTED_RESULTS_PATH` alongside it. To add a regression test for a new
gpkg-derived fixture, either:

- Parameterize `main_test.py` to iterate over `(input_zip, expected_geojson)`
  pairs, or
- Add a new test module that re-uses the helpers (`_post_testarea`,
  `_wait_for_completion`, `_assert_values_within_margin`) with the new paths.

The reference results GeoJSON can be generated by running the calculator
once against the new zip and snapshotting the `data.areas` response — same
shape as `test-data-small-polygon-results.geojson`.

## CLI reference

```
python tests/data/gpkg_to_testdata.py INPUT.gpkg OUTPUT.zip \
    --zoning-code CODE \
    [--landuse built,new_open,new_tree,existing] \
    [--layer LAYER_NAME] \
    [--name-prefix PREFIX]
```

- `--zoning-code` is required; it is applied to every feature regardless of
  what the source gpkg contains.
- `--landuse` is optional. When omitted, the output has no landuse columns and
  the calculator treats every feature as 100 % existing cover.
- `--layer` defaults to the first layer reported by `fiona.listlayers`.
- `--name-prefix` controls the generated `name` property
  (`<prefix>-1`, `<prefix>-2`, …).
